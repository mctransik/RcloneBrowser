# Scanned Windows ZIP: GitHub build provenance attestation (2026-10-15)

> Status: **CI validated 2026-10-15** for the exact scanned Windows archive; independent source review, Authenticode signing and Firefox warning investigation remain open. The public release job remains disabled.

## How the controlled provenance gate works

After the Windows job completes its Authenticode audit and the isolated Linux ClamAV job succeeds, a separate manually triggered **development-branch-only** job `windows_provenance` runs with minimal required GitHub attestation permissions (`contents: read`, `id-token: write`, `attestations: write`, `artifact-metadata: write`). Standard PR builds do not enter the write-capable attestation job.

1. Download the **promoted** `release-windows` Actions artifact (the original Windows application archive as its only file), plus the text-only `clamav-windows-scan-report` generated by the scanning job.
2. Strictly parse and independently SHA-256-check the exact packaged `RcloneBrowser-<version>-windows-x64.zip` bytes against the original post-scan `windows-zip.sha256`. Refuse basename differences, unrecognized report contents, multiple ZIP files or digest mismatches. The validator is unit-tested offline against deliberate tampering and malformed inputs.
3. Call the pinned official `actions/attest` action to generate a repository-linked SLSA build-provenance attestation for that exact Windows archive, **not** the extra GitHub Actions download-wrapper ZIP.
4. Immediately verify the cryptographic attestation using `gh attestation verify` while enforcing the current repository, `.github/workflows/update.yml`, full source commit (`--source-digest`) and development-branch source ref (`--source-ref`). A verification failure fails this job.
5. Upload `windows-provenance-verification` as a separate diagnostic with text-only digest, source metadata and verifier output. No historical EXE/DLL files are re-uploaded by this provenance job.

## Reproduce verification on a downloaded Windows ZIP

Download and **extract the GitHub Actions artifact wrapper** `release-windows` from a successful *provenance-verified* run. Run the command below **against the inner `RcloneBrowser-<version>-windows-x64.zip`**, before extracting/running the app:

```powershell
gh attestation verify ".\RcloneBrowser-4.0.2-windows-x64.zip" --repo mctransik/RcloneBrowser --signer-workflow mctransik/RcloneBrowser/.github/workflows/update.yml --source-ref refs/heads/feature/cloud-control-ui-mvp --source-digest <full-commit-sha>
```

Replace `<full-commit-sha>` with the complete expected SHA obtained from the intended reviewed workflow run. Verification should fail if even one byte of the ZIP changes or the requested provenance identity mismatches. The exact `gh attestation verify` command and options are documented by GitHub: https://cli.github.com/manual/gh_attestation_verify .

## Security and trust limitations

- A valid attestation **binds package bytes to a GitHub Actions identity and reported source**, not a malware-free verdict or independent source-code review. It is not a Windows Authenticode signature and will not necessarily resolve Firefox reputation warnings.
- This attestation runs in a separate downstream job after downloading the promoted package. It proves the attestation job verified the scanned ZIP bytes; it is **not** evidence that a hermetically isolated trusted builder compiled the executable. Stronger protection would require protected source branches, reviewed workflows and possibly a hardened reusable builder.
- The branch and its workflow remain editable during development. The signer identity alone does not prove the source was approved; release protections and reproducible/pinned dependencies still need separate work.
- The job emits public repository attestation metadata and its text verification report. It never signs the project EXE with a publisher certificate, adds a signing key or enables releases.
- GitHub Free/Pro/Team supports attestations for **public** repositories; the feature/permissions and runner CLI will be validated by the next workflow run. Any unsupported GitHub environment should cause an explicit failure, not a bypass.
